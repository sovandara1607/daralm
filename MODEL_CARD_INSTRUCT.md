# Model Card: DARALM-50M-INSTRUCT

> Part of the DaraLM project — a from-scratch decoder-only Transformer for Khmer + English, built as an educational/portfolio exercise. **Not a production or commercial-grade language model.** See the repo README for the full project.
>
> Unlike `MODEL_CARD.md` (auto-generated by `scripts/generate_model_card.py` from `experiments/evaluation_report.json`, which is built around base-pretraining metrics — packed-token perplexity, memorization-vs-raw-documents), this card is **hand-authored**. `scripts/evaluate.py`'s pipeline doesn't (yet) understand `InstructionDataset`'s loss-masked, non-packed batches, and extending it wasn't in scope. Every number below is real, pulled directly from `checkpoints/daralm-50m-instruct/history.json`, `best/meta.json`, `checkpoints/daralm-50m/best/meta.json`, and `data/raw/MANIFEST_instructions.json` — none of it is estimated or invented.

## The honest story behind this checkpoint

This is the **third** SFT run against this project's data, not the first, and the differences between the three attempts are worth knowing before reading the numbers below:

1. **Original Phase 9 run**: 100 steps on 324 examples (300 English Alpaca + 25 hand-authored Khmer), Base at step 300 (val perplexity 573.6). Final Instruct val perplexity: 194.4. Generation was short/degenerate (`The -thethecoral ⁇ /assistant>`).
2. **Bigger-dataset attempt**: found a real Khmer instruction dataset (`saillab/alpaca_khmer_taco`, ~50K rows) and expanded to 923 examples (500 English + 400 real Khmer + 25 hand-authored), retrained 300 steps on the *same* undertrained Base (still step 300). Final Instruct val perplexity got **worse**, not better: 290.4. Generation was *still* short/degenerate — no visible improvement despite 3x the data.
3. **This checkpoint**: diagnosed that Base's own undertraining (only 300 pretraining steps, ~4.9M tokens) — not the instruction dataset — was the real ceiling, since SFT can only nudge a base model's existing language ability, not manufacture fluency it never had. Continued Base pretraining from step 300 → 1500 (`configs/50m.yaml`, `--resume`), taking its validation perplexity from 573.6 → **182.0**. Redid SFT on the *same* 923-example dataset from attempt 2, on top of this substantially better Base. Result: Instruct val perplexity dropped to **110.7** — the best of all three attempts, and generation is visibly, substantially more fluent (see below).

The lesson, stated plainly: **more/better instruction data alone did not fix a base model that was itself still very undertrained.** Longer base pretraining was the actual fix. This is disclosed as a real research narrative, not smoothed into "we improved the model" — attempt 2 was a genuine dead end on its own, and is worth knowing about if you're deciding how to improve a small from-scratch LLM's instruction-following.

## Relationship to DaraLM-50M (Base)

DaraLM-50M-Instruct is DaraLM-50M **fine-tuned**, not trained from scratch. Base and Instruct are kept strictly separate:

- Identical architecture (must match exactly — SFT loads Base's `state_dict` directly): 512 hidden, 8 layers, 8 heads, 16,000 vocab, 1024 max position embeddings, 33,366,528 parameters.
- Different checkpoint directory (`checkpoints/daralm-50m-instruct/`, never overwrites `checkpoints/daralm-50m/`).
- Different training data, objective, and hyperparameters (below).
- Initialized from `checkpoints/daralm-50m/best` at **step 1500** (val_loss 5.204, perplexity 182.0) — not step 300 as in the first two attempts. Only weights were carried over — optimizer/scheduler state was **not** loaded, so SFT starts a fresh Adam state and its own step counter at 0.

## Chat Template

```
<bos><user>
{instruction}
</assistant>
```

`<bos>`/`<eos>` are the tokenizer's real special tokens. `<user>`, `</user>`, `<assistant>`, `</assistant>` are **plain text**, not new special tokens — added as literal characters, tokenized as ordinary subwords, so Base's exact vocabulary/embedding shape never had to change. See `daralm/data/chat_template.py`.

**Known tokenizer caveat**: the tokenizer was trained only on Wikipedia article text, which contains essentially no `<`/`>` characters. As a result `<` has no dedicated subword piece and is encoded/decoded through the `<unk>` token — decoded output shows the placeholder glyph `⁇` where a literal `<` should appear (e.g. `⁇ /assistant>`). Internally consistent (a fixed, learnable token sequence), but a real, still-unfixed cosmetic issue. Still present in this checkpoint's generation (see below) — the improvement from longer Base pretraining did not touch this, since it's a tokenizer-vocabulary limitation, not a fluency one.

## Training Data (SFT)

923 instruction/response pairs (`data/cleaned/instructions_{train,val,test}.jsonl`: 784 train / 138 val / 1 test), from three sources recorded in `data/raw/MANIFEST_instructions.json`:

- **English (500 examples)**: a random sample of `tatsu-lab/alpaca`, filtered to examples with no separate `input` field. License: CC BY-NC 4.0 — **non-commercial**.
- **Khmer, real (400 examples)**: `saillab/alpaca_khmer_taco`, a ~50K-row Khmer translation of Alpaca (TaCo-paper style). No explicit license tag on the HF dataset page — treated as inheriting Alpaca's CC BY-NC 4.0, since it's a derived translation, not an independently-licensed dataset. Required non-trivial parsing: the dataset's `output` field is a compound string (`"Instruction in English: ... Response in English: ... Response in Khmer: ..."`), and its `input` field encodes "empty" as the literal string `"nan"` rather than `None` — both handled in `daralm.data.loader.fetch_alpaca_khmer_sample`.
- **Khmer, hand-authored (25 examples)**: kept from the original Phase 9 set as a small supplement, not the primary Khmer source anymore.

2 records (of 925 fetched) were dropped for being too short; 0 exact duplicates found.

No sequence packing: each pair padded individually to `block_size=768` (bumped from 512 after the dataset expansion — measured real tokenized lengths: p50=115, p90=332, max=695 tokens; 512 would have silently dropped 18 examples, ~2% of the set).

## Loss Masking

Only the response portion of each example contributes to the training loss — `InstructionDataset` sets `labels` to `pad_token_id` (cross-entropy's `ignore_index`) at every prompt-token position, and the real token ID at every response-token position.

## Training Configuration

| | |
|---|---|
| Optimizer | adamw (fresh state, not resumed from Base) |
| Learning rate | 0.00005 |
| Weight decay | 0.1 |
| Precision | bf16 |
| Batch size (micro / accumulation) | 4 × 4 |
| Max steps | 300 (~6 epochs over 784 train examples) |
| Warmup steps | 30 |
| Seed | 42 |

`batch_size=4` re-measured (not assumed) safe at `block_size=768`: isolated timing found batch=4 → 0.510s/step, batch=8 → 1.379s/step (a real but mild slowdown), batch=16 → **crashed outright with an MPS out-of-memory error** (17.54 GiB allocated) — a different failure mode than the throughput cliffs found at other shapes in earlier phases, not just a repeat of the same one.

## Training Tokens

3,686,400 tokens processed (16 sequences/step effective batch × 768 tokens/sequence × 300 optimizer steps) — on top of Base's own 24,576,000 pretraining tokens (5x more than the first two SFT attempts saw Base trained on).

**Honest read — real progress, and a real gap that remains**:

- **English generation is genuinely, visibly better** than either previous attempt. Both Base and Instruct now produce long, grammatically coherent sentence structures (proper clauses, capitalization, punctuation) — a categorical change from the earlier `⁇ /assistant>`-dominated or near-empty Instruct outputs. It's still **factually wrong and often repetitive** ("has has a result of a result of", "major major cities", "late late 1960s") — this is fluency, not accuracy, and shouldn't be mistaken for the model "knowing" anything.
- **Instruct no longer collapses to near-empty responses on English prompts.** This was the single most visible failure mode in both earlier attempts; it's gone here, replaced by full (if rambling) paragraphs.
- **Khmer generation in Instruct is still weak** — the Thailand-capital response is nearly as short/degenerate as attempt 1 and 2's outputs (`សរុប - - ⁇ /assistant>`, "Total - -" then the closing marker). This did **not** improve at the same rate as English, despite Khmer being 46% of the SFT dataset and roughly half of Base's own pretraining corpus by document count. This asymmetry is a genuine, unresolved gap — plausibly because Base's own Khmer fluency (see the Khmer sample above — still fairly incoherent, though wordier than earlier checkpoints) still lags its English fluency, and SFT inherits that gap rather than closing it.

## Known Limitations

- **Fluent-sounding but not accurate.** Longer base pretraining fixed grammatical fluency, not factual correctness — every example above is confidently wrong. Don't mistake coherent sentence structure for knowledge.
- **Khmer lags English.** A real, measured gap: English responses are now substantially longer and more structured; Khmer responses remain short and often degenerate into the `</assistant>` marker almost immediately. Not yet understood whether this is a Base-fluency gap, an SFT-data-composition issue, or something else — flagged as open, not resolved.
- **Chat markers still render with `⁇` placeholders**, per the tokenizer caveat above — unaffected by any of this round's changes, still a real, disclosed, unfixed issue.
- **No safety tuning, no preference data (RLHF/DPO), no red-teaming.** Instruction-format fine-tuning only.
- **SFT dataset is still English-skewed at the raw-example level** despite the improved balance (500 English : 425 Khmer is close to 1:1 by count, but Khmer's translation quality/naturalness — via TaCo's LLM-translation pipeline — is an open question this project hasn't independently audited).

## Responsible Use

This model is a **learning artifact**. It is not evaluated or intended for factual, medical, legal, financial, or safety-critical use. Fluent-looking output that is factually wrong is the primary failure mode to watch for — don't let improved grammar read as improved correctness.
