# Model Card: DARALM-50M-INSTRUCT

> Part of the DaraLM project — a from-scratch decoder-only Transformer for Khmer + English, built as an educational/portfolio exercise. **Not a production or commercial-grade language model.** See the repo README for the full project.
>
> Unlike `MODEL_CARD.md` (auto-generated by `scripts/generate_model_card.py` from `experiments/evaluation_report.json`, which is built around base-pretraining metrics — packed-token perplexity, memorization-vs-raw-documents), this card is **hand-authored**. `scripts/evaluate.py`'s pipeline doesn't (yet) understand `InstructionDataset`'s loss-masked, non-packed batches, and extending it wasn't in scope for Phase 9. Every number below is still real, pulled directly from `checkpoints/daralm-50m-instruct/history.json`, `best/meta.json`, and `data/raw/MANIFEST_instructions.json` — none of it is estimated or invented.

## Relationship to DaraLM-50M (Base)

DaraLM-50M-Instruct is DaraLM-50M **fine-tuned**, not trained from scratch. Per spec section 24, Base and Instruct are kept strictly separate:

- Identical architecture (must match exactly — SFT loads Base's `state_dict` directly): 512 hidden, 8 layers, 8 heads, 16,000 vocab, 1024 max position embeddings, 33,366,528 parameters.
- Different checkpoint directory (`checkpoints/daralm-50m-instruct/`, never overwrites `checkpoints/daralm-50m/`).
- Different training data, objective, and hyperparameters (below).
- Initialized from `checkpoints/daralm-50m/best` (Base's best validation checkpoint, step 300, val_loss 6.35). Only weights were carried over — optimizer/scheduler state was **not** loaded, so SFT starts a fresh Adam state and its own step counter at 0, rather than "resuming" pretraining.

## Chat Template

```
<bos><user>
{instruction}
</assistant>
```

`<bos>`/`<eos>` are the tokenizer's real special tokens. `<user>`, `</user>`, `<assistant>`, `</assistant>` are **plain text**, not new special tokens — added as literal characters, tokenized as ordinary subwords, so Base's exact vocabulary/embedding shape never had to change. See `daralm/data/chat_template.py`.

**Known tokenizer caveat, discovered during Phase 9 evaluation:** the Phase 2 tokenizer was trained only on Wikipedia article text, which contains essentially no `<`/`>` characters. As a result `<` has no dedicated subword piece and is encoded/decoded through the `<unk>` token. This is internally consistent — the model still sees a fixed, learnable token sequence for every marker — but it means decoded output shows the placeholder glyph `⁇` where a literal `<` should appear (e.g. `⁇ user>` instead of `<user>`). This wasn't anticipated when the plain-text-marker design decision was made, and no fix was implemented in Phase 9: the token IDs remain the ground truth for training/evaluation, and this is disclosed here rather than in a churn-inducing tokenizer retrain mid-project. A future tokenizer retrain including markup characters in its training corpus is the correct fix, tracked as future work, not done here.

## Training Data (SFT)

324 instruction/response pairs (`data/cleaned/instructions_{train,val,test}.jsonl`: 275 train / 48 val / 1 test), from two sources recorded in `data/raw/MANIFEST_instructions.json`:

- **English (300 examples)**: a random sample of `tatsu-lab/alpaca` (via Hugging Face `datasets`, streamed), filtered to examples with no separate `input` field. License: CC BY-NC 4.0 — **non-commercial**. This project is educational/portfolio use only; this source must be swapped before any commercial use.
- **Khmer (25 examples)**: hand-authored for this project. No suitable public Khmer instruction-tuning dataset was available at this scale. Short, factual, low-risk Q&A pairs (capitals, basic science, arithmetic) — clearly labeled `"source": "handauthored"` in every record, never presented as sourced data.

1 record (of 325 fetched) was dropped for being too short; 0 exact duplicates found. Both sources go through the same clean → dedupe → split pipeline as Phase 1's base corpus (`scripts/prepare_instruction_dataset.py`), reusing `daralm.data.cleaner.clean_text`, `daralm.data.deduplication.deduplicate`, and `daralm.data.dataset.split_dataset` rather than a parallel implementation.

No sequence packing: each instruction/response pair is padded individually to `block_size=512` (not `max_position_embeddings=1024`) — chosen after measuring real tokenized example lengths (p50=103, p90=195, max=490 tokens with the trained tokenizer + chat template), so no example needed to be dropped for exceeding it.

## Loss Masking

Only the response portion of each example contributes to the training loss — `InstructionDataset` sets `labels` to `pad_token_id` (cross-entropy's `ignore_index`) at every prompt-token position, and the real token ID at every response-token position. The model is never scored on predicting the instruction it was given, only on generating a good response to it. This required zero changes to `DaraLMTransformer.forward`, which already accepted `input_ids` and `labels` as independent tensors — base pretraining just always happened to call it with `labels is input_ids`.

## Training Configuration

| | |
|---|---|
| Optimizer | adamw (fresh state, not resumed from Base) |
| Learning rate | 0.00005 (30x lower than Base's 0.0003 — SFT nudges an already-trained model, it doesn't relearn language from scratch) |
| Weight decay | 0.1 |
| Precision | bf16 |
| Batch size (micro / accumulation) | 4 × 4 |
| Max steps | 100 (~6 epochs over 275 train examples) |
| Warmup steps | 10 |
| Seed | 42 |

`batch_size=4` reuses the exact shape Phase 6-7 measured as safe on this hardware's Apple Silicon MPS backend. Re-measured for this phase's shape (block_size=512, not Base's 1024) before training, not assumed: isolated single-step timing found batch=4 → 0.29s/step, batch=8 → 0.64s/step, batch=16 → **22.3s/step** — the same severe MPS throughput-cliff pathology Phase 6 found at a different sequence length, confirming batch_size=4 was still the right, safety-margined choice rather than an untested carryover.

## Training Tokens

819,200 tokens processed (16 sequences/step effective batch × 512 tokens/sequence × 100 optimizer steps) — on top of whatever Base saw during its own pretraining (~4.9M tokens, see `MODEL_CARD.md`).

## Evaluation Results

Real numbers from `checkpoints/daralm-50m-instruct/history.json`:

| step | train_loss | val_loss | perplexity |
|---|---|---|---|
| 5 | 6.442 | — | — |
| 20 | 5.702 | 5.730 | 308.0 |
| 40 | 5.631 | 5.413 | 224.3 |
| 60 | 5.451 | 5.317 | 203.8 |
| 80 | 4.949 | 5.282 | 196.7 |
| 100 | 4.988 | 5.270 | 194.4 |

Both train and validation loss decreased steadily and val_loss was still improving at the final step (best checkpoint = final checkpoint, step 100) — no overfitting signal within this short run, consistent with only ~6 epochs over a small dataset at a low learning rate.

**Base vs. Instruct generation, same prompts** (temperature=0.8, top_k=40, real output, not cherry-picked):

| Prompt | Base (raw continuation) | Instruct (chat-templated) |
|---|---|---|
| "What is the capital of France?" | `...In a a role of the first-Nrery's, the city were not over theirly...` | `The -thethecoral ⁇ /assistant>` |
| "Describe the process of photosynthesis in one sentence." | `...The end of the city, as the s of the s of the same time...` | *(empty response)* |
| "តើរាជធានីនៃប្រទេសថៃមានឈ្មោះអ្វី?" (What is Thailand's capital?) | `...លាងឲ្យលោក និង នសលមានមាននេះ យ ទឹក ទឹក...` | `⁇ /assistant>` |

**Honest read of this table**: neither model produces a coherent, correct answer — expected at this scale (33M parameters, ~4.9M pretraining tokens, ~820K SFT tokens; production instruction-tuned models see orders of magnitude more of both). What SFT visibly changed is *structural*, not factual: Instruct's outputs are short and gravitate toward emitting the `</assistant>` closing marker quickly (sometimes producing almost nothing before it), rather than continuing to ramble the way Base does. That's the loss-masking objective doing something real — the model shifted toward "stop after a short response" — but at 100 steps on 275 examples it has not yet learned *what* to say, only roughly *when to stop*. Whether that's "some structural improvement" or "learned to produce empty/near-empty responses to minimize loss on a tiny dataset" is genuinely ambiguous from 100 steps of data; presented here as the real, unresolved finding it is, not smoothed over in either direction.

## Known Limitations

- **Not fluent, same as Base.** Everything in `MODEL_CARD.md`'s "Known Limitations" applies here too — this model inherits Base's language ability and this SFT run did not meaningfully improve it (nor was it expected to, at this scale/token count).
- **Degenerate short/empty responses.** As shown above, Instruct sometimes produces near-empty output. This looks like the model latching onto "close the turn quickly" as a low-loss strategy given very little SFT data, not learned conversational brevity.
- **Chat markers render with `⁇` placeholders**, per the tokenizer caveat above — a real, disclosed cosmetic (and potentially training-signal-diluting) issue, not fixed in this phase.
- **No safety tuning, no preference data (RLHF/DPO), no red-teaming.** This is instruction-format fine-tuning only, exactly as scoped for Phase 9 — nothing about alignment or safety was in scope.
- **SFT dataset is tiny and English-skewed** (300 English : 25 Khmer). The Khmer half exists at all only because it was hand-authored for this project — there was no readily available public Khmer instruction dataset. This imbalance is a real limitation of the current Instruct model, not a hidden one.

## Responsible Use

This model is a **learning artifact**, built to understand the SFT step of the LLM training pipeline end to end. It is not evaluated or intended for factual, medical, legal, financial, or safety-critical use of any kind. Outputs should not be presented to end users as authoritative, and the near-empty/degenerate response pattern documented above should be treated as expected behavior at this scale, not a serving bug to route around.
